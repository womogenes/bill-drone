# ESP32-CAM AprilTag pose

One firmware handles onboard tag16h5 pose estimation, SPI delivery, Wi-Fi preview, lens calibration, and passwordless OTA. It targets the AI Thinker ESP32-CAM with a driver-detected sensor (OV3660 on this board), 4 MB flash, and PSRAM. The drone's receiver is `fw/drone/main/camera.c`.

## Wiring

| Signal | ESP32-CAM | Main ESP32 | Direction |
|---|---:|---:|---|
| SCLK | GPIO14 | GPIO27 | Main → CAM |
| MOSI | GPIO13 | GPIO26 | Main → CAM |
| MISO | GPIO12 | GPIO34 | CAM → main |
| CS | GPIO15 | GPIO23 | Main → CAM |
| READY | GPIO2 | GPIO4 | CAM → main |

Signals are 3.3 V; share ground through the power wiring. Leave the camera's microSD slot unused. Main GPIO34 must remain an input without pull-up, preserving camera GPIO12's low boot strap. Main GPIO4 uses a pull-down, keeping camera GPIO2 low for serial flashing. CS idles high. Keep the signal wires short.

## Flash and update

Copy `src/wifi.example.h` to git-ignored `src/wifi.h` and set network credentials. The local header has been populated from the repository `.env`. OTA has no password. From `src/`, build and initially flash **the camera's verified programmer port**:

```sh
uvx --from platformio==6.1.18 --with intelhex pio run -d fw/esp32cam
uvx --from platformio==6.1.18 --with intelhex pio run -d fw/esp32cam -t upload --upload-port /dev/ttyUSB_CAM
```

Ground camera GPIO0 and reset/power-cycle for serial flashing; release GPIO0 and reset afterward. Identify the board before selecting a port: USB numbers can move, and these two adapters have identical USB serial numbers. The CAM identified on 2026-10-19 has MAC `58:2A:BD:79:2B:9C`, physical path `/dev/serial/by-path/pci-0000:c1:00.3-usb-0:1:1.0-port0` (then USB1). The main controller was USB0 and printed `Starting app...`. Reconfirm if wiring changes.

Subsequent firmware updates:

```sh
uvx --from platformio==6.1.18 --with intelhex pio run -d fw/esp32cam -e ota -t upload
```

Hostname: `bill-esp32cam.local`; override with `--upload-port <camera-ip>` when mDNS is unavailable. The first flash installs two 1.25 MiB OTA slots. Updates pause processing and reboot the CAM; update while the flight controller is disarmed.

## Dashboard calibration and preview

Open **Camera** (`/camera`) in the dashboard and connect. Enter the printed **tag16h5 ID (0–29)** and **outer black-square width in millimetres**, excluding the white margin. Capture **25–40 sharp views of the same flat tag**, varying both tilt axes, distance, and position across the image while keeping all corners visible. Press Space or click Capture view; Space is ignored while typing in inputs. A single tag has only four corners, so varied views are especially important.

**Calibrate and save** runs `calibration.py` with `src/.venv/bin/python`, fits the lens, writes `src/config.h`, and sends the calibration to the CAM's `/config` endpoint. The CAM applies it immediately and stores it in NVS across reboots. Saved NVS calibration takes precedence over compiled defaults. No reflashing is needed to calibrate. A failed camera connection leaves the local fit saved, but the dashboard reports failure until it is applied to the board.

The fit uses focal lengths, principal point, and two radial distortion coefficients; tangential distortion and k3 are fixed to zero because a single tag supplies few constraints. Reprojection RMS must be below 1 px; a small RMS alone does not prove accuracy. Check measured distances after calibration and recalibrate after changing focus, lens, resolution, crop, or orientation. Both detection and preview use the same upright 320×240 raw grayscale (Y8) capture of the sensor's central 1536×1152 window, with hmirror=0 and vflip=1. These settings rotate the previous image 180 degrees. The dashboard applies no additional display flip. Calibration is stored separately for this orientation; recapture views after switching to it. The preview JPEG is encoded from the detector's own frame, so calibration sees the same geometry. The compiled calibration was derived on 2026-10-21 from the 2026-10-19 full-window fit (focal lengths ×4/3, principal point shifted for the crop); the measured tag distance agreed within 0.4%. Saved calibration lives under a new NVS key for this geometry, so the old fit is not applied. Recalibrate for best accuracy; k2 = 0.90 from a four-corner fit is suspect.

Preview is MJPEG on camera port 81, proxied through the dashboard, at up to 15 fps. When the preview asks for a frame, the detector hands over the frame it just finished instead of returning it to the driver; the low-priority HTTP task on core 0 encodes it, returns it and sends the JPEG. The detector never copies or encodes video. With two frame buffers, a frame held for encoding delays the next capture, and the detector's internal-RAM placement is off while streaming, so a viewer lowers the pose rate. Without a viewer nothing is encoded. The dashboard shows actual preview fps and detector Hz. SPI reception can be absent without stalling capture, detection, preview, or OTA.

## Pipeline and timing

The OV3660 reads the central 1536×1152 of its 2048×1536 array, binned and scaled 2.4× to 320×240 Y8, at 29.4 fps: 576 of 591 lines at 57.5 µs each (40 MHz SYSCLK, 10 MHz PCLK), so a frame takes 33 ms to read out. Against the full field this gives 4/3 the angular resolution over 36°×27°. The JPEG-mode 50 MHz clock (46 µs lines) stalled the driver's DMA copy and the CAM panicked within minutes, even with the detector idle in internal RAM, so 57.5 µs is the line-rate floor at 320 pixels wide. Core 1 runs capture, the tag search, pose and SPI; core 0 runs the image flow, Wi-Fi, OTA, `/status`, `/config`, the preview and the driver's DMA copy.

Two frame buffers in PSRAM with `CAMERA_GRAB_LATEST`. The driver's queue is first in, first out, so more buffers only return older frames; with two, the driver stops capturing while the detector holds one and the other waits. A fetched frame more than two frame periods old is returned and the next capture used. About 0.3 to 0.5% of frames arrive short (the driver's `FB-SIZE` error: one 12-line DMA block missing) and are dropped by the driver, whatever the line rate, the flow task or Wi-Fi power saving; together with other dropped frames the delivered rate is about 95% of the sensor's. On 2026-10-21 one run of such failures lasted past the driver's 4 s timeout, a stall. Now a stall restarts the camera (up to three tries) and counts `stalls` and `recoveries` in `/status`; only if all three fail does `/status` say `"camera":"stalled"`. Wi-Fi and OTA stay up either way. `/log` returns the last 2 KB of ESP-IDF log output (the driver's errors), and `short_frames` counts the `FB-SIZE` errors. `last_crumbs` records, across a panic restart, which step each core was in before the last reset.

Exposure is fixed at 10 ms (174 lines) with automatic gain up to its 64× ceiling, so motion blur stays a third of a full-frame exposure. Every 15 frames, if the gain is above 56× the exposure grows by a quarter (up to the whole frame), and below 24× it shrinks back toward 10 ms. The sensor's own exposure control ran at the full 33 ms frame and ignored its exposure limit registers. Measured on 2026-10-21 at 1.7 m in the brighter light, against exposure: 33 ms needed 8.25× gain (position standard deviation 4.4, 3.2, 1.8 mm), 17 ms 15.8× (5.7, 4.1, 2.2 mm), 10 ms 26.6× (8.6, 5.9, 3.3 mm), 5 ms 55 to 62× (14, 11.6, 6 mm), all 100% valid.

Once the tag is found, each frame re-measures it with `track.h` instead of the detector: from the corners predicted by the last two frames, about 30 intensity profiles across each edge locate the edge to a fraction of a pixel (the step's area over its height, which is exact for any blur), a weighted line is fitted per edge, and the corners are the lines' intersections. The tag's 16 data bits are then read through the new corners and must match its code with at most one bit wrong, so every pose is measured from that frame's pixels. The tag's neighbourhood is first copied to internal RAM. This takes 4 to 5 ms. In simulation its corners are as accurate as the detector's (0.05 px with little noise, 0.19 px at noise σ 15 against the detector's 0.18). The AprilTag detector (`detectTag`) runs only to acquire or recover the tag: in a window around the prediction when one exists, else the whole frame, with the decimation and cluster limits sized to the tag. Its corners are shifted by half a pixel into the calibration's convention (pixel centres at integers): in simulation that cut the detector's corner error from 0.73 to 0.09 px. The detector library is built at -O2 with float constants and float math calls, and with one task per stage instead of ten (`build.py`).

The pose is solved in closed form by IPPE (`pose.h`, as OpenCV's `SOLVEPNP_IPPE_SQUARE`), giving both planar solutions in about 0.1 ms with no allocation. The capture time is the readout time of the tag's centre row (rolling shutter, 138 µs per output row), or of the frame's centre row when there is no tag.

The flow (`flow.h`) runs on core 0 while core 1 tracks the tag. It reduces the frame to 80×60 (one row in four, four pixels averaged), picks the 12 blocks of the previous reduced frame with the most texture in both directions outside the predicted tag, finds each in the current one by sum of absolute differences within ±4 small pixels, refines with two Lucas-Kanade steps, and reports the mean shift of the blocks within one small pixel of the median, in full-resolution pixels, with the inlier count and the median deviation. It takes about 6 ms; in simulation the shift error is 0.05 to 0.1 px.

Measured on 2026-10-21 over a 35-minute soak in the brighter light (10 ms exposure, gain about 24×), 151 mm tag 1.70 m away, polling `/status` once a second from another host: no stalls, no reboots, 27.9 Hz delivered (the sensor runs 29.4 fps), tag-row age at READY median 36.5 ms (p90 40.7, max 46.1), frame-start age median 40.9 ms, frame fetch to packet queued median 7.0 ms, 99.9% of frames valid, every frame tracked after acquisition, tracker margin about 46, reprojection RMS median 0.11 px, camera position standard deviation 8.8, 5.6 and 3.3 mm (x, y, z), flow standard deviation 0.02 and 0.03 px per frame with the camera still. An earlier 35-minute soak at the sensor's full-frame exposure also had no stalls. Almost all of the camera-in-tag jitter is tilt noise times distance (the tag's position in the camera frame varies by tenths of a millimetre across), which the drone's attitude can replace. `/status` reports `detect_us` (frame fetched to packet queued), `frame_us` (capture interval), `age_us` (tag-row age), `frame_age_us`, the tracked and detected counts, the flow, `gain`, `exposure_lines`, the lowest free internal RAM since boot (`internal_min`), `uptime_ms` and the reset reason. A packet older than 150 ms is sent with valid cleared.

Faster frame rates were tried on 2026-10-21 and dropped. At 10 MHz PCLK a 320-pixel line needs 32 µs, so 100 fps requires 160×120: with 80 MHz SYSCLK and 1300-cycle lines the sensor delivered 101.5 Hz (detection off), with 21-pixel tags and half the resolution. In the room's light at that time its 9.6 ms exposure detected nothing, and whole-frame searches with frame buffers in DRAM drove internal RAM down to 5 KB and panicked. `config.h` records those settings.

## Drone receiver

`fw/drone/main/camera.c` is built into the drone firmware but not started. `camera_start()` sets up SPI2 at 4 MHz in mode 1 and a rising-edge interrupt on READY that wakes a receiver task on core 0, which clocks the packet at once. The receiver checks magic and CRC, refuses a repeated sequence and any packet older than 150 ms on arrival, and stamps the capture time on the drone clock as the READY edge minus the camera's age. A READY found high with no edge (at start, or after a missed edge) is read and discarded. The newest frame decides: a frame without the tag clears the pose. Control reads `camera_pose(&pose, max_age_us)`, which carries the valid kind, and uses each sequence once. `camera_flow(&flow, max_age_us)` gives the newest frame's image shift, interval and quality with its capture time on the drone clock; for velocity, subtract the rotational flow (fx or fy times the gyro rate over the interval, in the camera axes) and scale the rest by depth (the tag's z, or another estimate). `camera_stats()` gives link counters.

## Coordinate frames and packet

`point_tag = rotation * point_camera + position_m`. Position is the camera origin in metres in the tag frame. Rotation is a row-major 3×3 matrix, camera → tag. Camera axes are image-right, image-down, and through the lens. Tag axes are right, down, and into the printed tag in its canonical orientation. A camera facing the tag has negative tag-frame Z. Measure the camera mounting transform before body pose hold: `T_tag_body = T_tag_camera * inverse(T_body_camera)`.

SPI mode 1, MSB-first, 4 MHz, exactly 100 bytes per READY. Packet fields are little-endian integers and float32; Python format `<4sIIIHH16fIfHhHH`: magic `TAG2`, sequence, capture time (µs), age (µs), tag ID, valid, position[3], rotation[9], margin, reprojection RMS, flow[2] (px, right and down, previous frame to this), flow interval (µs, 0 without flow), flow residual (px), flow inliers, flow offset (µs, this frame's centre-row readout minus the capture time), reserved zero, CRC-16/CCITT-FALSE over 98 bytes. The margin is the detector's decision margin when it found the tag, else the tracker's mean distance of the bit samples from the black-white threshold, in grey levels. A pose is valid only when the tag was acquired by exactly one detection of the configured ID with zero bit errors and decode margin at least 30 and has been tracked since with its code matching, the reprojection RMS is at most 2 px, and the packet is under 150 ms old. Valid is 1 when the second planar solution's squared error is more than twice the best one's, using a 0.3 px RMS floor below which both fit within corner noise. Otherwise the tilt is ambiguous, as it usually is for this tag beyond about 1.5 m: valid is 2 when the solution nearest the last valid pose (from the past 500 ms) is within 20° of it, and 0 if not. A pose resolved by continuity is only as right as the unambiguous pose that started the chain. Invalid packets still go out every frame with zero pose, so the receiver sees the camera is alive. Capture time is the readout of the tag's centre row on the CAM clock (the driver stamps the start of the frame; each output row follows 138 µs later); exposure ended at that readout. Age is capture-to-ready on the CAM; the receiver adds how long READY was high and the transfer. Both sides expire packets after 150 ms.

`main.cpp` owns capture, the tag search and SPI; `track.h` the edge tracker; `flow.h` the image flow; `pose.h` geometry; `web.h` owns preview and calibration persistence; `ota.h` owns Wi-Fi/OTA. `build.py` builds the detector and `main.cpp` at -O2, gives the detector float math and one task per stage, and moves its cold files to flash so Wi-Fi and camera interrupt code still fit in IRAM. Vendor code is pinned and unchanged. Bench-test calibrated accuracy and main-controller loop timing before using vision for pose hold.
